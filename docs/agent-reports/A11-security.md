# A11 — Security, Privacy & Compliance report

## Work done
1. **G6 brute-force protection**
   - Per-account lockout: `users.failed_login_count`, `users.locked_until`. 5 consecutive wrong passwords → locked 15 min; success resets; atomic `UPDATE … RETURNING` increment (no lost updates under concurrency); attempts while locked do not extend the lock (bounds DoS).
   - Per-IP sliding window on `POST /api/v1/auth/login`: counts **failed** attempts (default 20 / 300 s) → `429 {"detail":"Too many login attempts. Try again later."}` + `Retry-After`. Redis sorted-set window when `HRSWI_REDIS_URL` is reachable, in-process (LRU-bounded) otherwise; Redis errors fall back to in-process. Successful logins are not counted so shared NATs / E2E runs are not blocked, and cannot reset the window.
   - **Decision: locked accounts return the same 401 `{"detail":"Invalid credentials"}` as wrong credentials** (a 429 on lock would reveal that the account exists). Unknown e-mail, wrong password, inactive and locked all run exactly one scrypt (fixed a timing leak: inactive users previously skipped scrypt).
   - Env: `HRSWI_LOGIN_PROTECTION_ENABLED`, `HRSWI_LOGIN_LOCKOUT_THRESHOLD`, `HRSWI_LOGIN_LOCKOUT_MINUTES`, `HRSWI_LOGIN_IP_MAX_FAILURES`, `HRSWI_LOGIN_IP_WINDOW_SECONDS` (read at call time; tests monkeypatch `bruteforce.settings` / `bruteforce.now`).
   - Audit: `auth.login_failed` (details: consecutive_failures / reason inactive), `auth.locked` (threshold_reached / attempt_while_locked), `auth.rate_limited` (retry_after_seconds), `auth.login`.
2. **Token revocation**: `users.token_version`; JWT carries `tv` (now a required claim); `get_context` rejects missing/non-int/stale `tv` (and non-integer `sub` → 401 instead of 500). `POST /api/v1/auth/logout-all` increments it (audited `auth.logout_all`), returns `{"status":"ok"}`. `create_access_token(user_id, tenant_id, token_version)` — third arg is now required (only caller is the login endpoint).
3. **B-03 retention**: `app/services/retention.py` `purge(db, *, now, staging_days=90, review_days=90, dry_run=True) -> dict` + CLI `python -m app.services.retention [--apply] [--staging-days N] [--review-days N]`. Committed/failed batches older than N days (by `import_batches.updated_at`): `raw → {}`, `mapped` keeps only `legal_entity_code, start_date, end_date, contract_type, termination_category, project_code, occupation_code, source_system, errors`; `errors` column kept. Purged **failed** batches become status `expired` (so a retry cannot commit half-empty rows). Resolved (`merged`/`rejected`) review items older than N days: `payload → {}`. Analytics tables never touched. Apply writes `retention.purge` audit rows (one per affected tenant + a summary row with tenant_id NULL) in the same transaction. Idempotent. Done in set-based SQL (PostgreSQL json functions).
4. `docs/SECURITY_PRIVACY.md` updated (G6 implemented with tests, token revocation, retention, G5 partially closed, new G10, breach procedure step).

## Residual risks / follow-ups
- G1 OIDC/MFA, G2 JWT in localStorage (httpOnly/BFF), G3 no PostgreSQL RLS, G4 at-rest encryption/KMS: still open.
- Lockout lets an attacker who knows an e-mail keep that account locked (one 15-minute lock at a time). Spreading guesses over many IPs is held back only by the per-account lock. There is no CAPTCHA.
- The IP limiter works per worker without Redis. Behind a proxy, uvicorn needs `--proxy-headers --forwarded-allow-ips`.
- Retention is not scheduled yet (DevOps: a daily `--apply` job). `data_quality_issues.record_ref` (external id) and messages are not purged. No retention policy table for HR/payroll/audit data (G5).
- Revocation covers all of a user's tokens at once. There is no single-session (jti) revoke, and a password change does not bump `token_version` yet (there is no password-change endpoint).
- The Orchestrator should add the `tv` claim, the 429 + Retry-After response and `POST /auth/logout-all` to `INTEGRATION_CONTRACTS.md` §1 (I don't own that file). The frontend may want to handle 429 and show a logout-everywhere action.
- A06's user deactivation needs nothing more: `is_active=false` already blocks tokens (`test_deactivated_user_token_rejected`). Bumping `token_version` on deactivation as well would be optional defence in depth.
